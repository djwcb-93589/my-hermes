# 新功能接入指南

这份指南用于快速判断一个新功能应该放在哪里、需要修改哪些模块，以及怎样接入 CLI、Gateway、Cron 和 Delegate。

## 基本原则

- 业务能力先实现为普通 Python 接口，再按需包装成模型工具。
- 工具只在全局 `ToolRegistry` 注册一次，不在不同入口维护工具名白名单。
- 只声明功能真正支持的运行环境，不默认开放给所有会话。
- 与远程消息无关的功能不要放进 `GatewayRunner`。
- 只有需要跨进程恢复、审计或长期保存的数据才进入 SQLite。
- Cron 是无人值守环境，必须显式申请 toolsets，并受 `CronCapabilityGrant` 限制。

## 普通工具接入

一个普通工具通常只涉及：

```text
hermes/tools/<tool_name>.py       业务接口、模型 handler、schema 和 register()
hermes/tools/__init__.py          在 register_all() 中注册模块
```

推荐把实现分成三层：

```python
def perform_action(query: str, *, limit: int) -> dict:
    """程序内部可直接复用的业务接口。"""
    ...


def handle_action(args: dict, **kwargs) -> str:
    """把模型参数转换成业务参数，并序列化结果。"""
    result = perform_action(
        str(args.get("query", "")),
        limit=int(args.get("limit", 5)),
    )
    return json.dumps(result, ensure_ascii=False)


def register(registry) -> None:
    registry.register(
        name="example_action",
        toolset="example",
        schema=EXAMPLE_SCHEMA,
        handler=handle_action,
        execution_environments=("cli", "gateway"),
        unattended_allowed=False,
        approval_mode="none",
        risk_level="low",
        default_enabled_environments=(),
        retry_safe=True,
    )
```

注册完成后，还要在 `hermes/tools/__init__.py` 的 `register_all()` 中调用新模块的 `register()`。工具定义和实际 dispatch 白名单会由统一解析器根据当前环境、toolsets 和策略生成。

### 工具元数据怎么选

| 字段 | 含义 |
|---|---|
| `toolset` | 用户或任务申请能力时使用的分组名 |
| `execution_environments` | 支持 `cli`、`gateway`、`cron`、`delegate` 中的哪些环境 |
| `unattended_allowed` | 是否允许在无人值守任务中运行 |
| `required_trusted_context` | 是否依赖可信 Gateway、Cron 或其他内部上下文 |
| `approval_mode` | 无审批、交互审批或远程一次性审批 |
| `risk_level` | 工具总体风险等级 |
| `default_enabled_environments` | 哪些环境可以默认启用该 toolset |
| `retry_safe` | 进程中断后是否能安全重试 |

不要因为工具当前看起来只读，就随意声明 `retry_safe=True`。如果调用会向外部服务写数据、发送消息或创建资源，应使用幂等键或状态查询，否则按结果未知处理。

## 需要审批的工具接入

当工具会修改文件、执行命令、向外部服务发送内容或产生其他需要用户确认的副作用时，工具注册和审批注册必须一起完成。只把 `approval_mode` 改成需要审批还不够：运行时还必须知道怎样重建这次操作的身份，以及批准后要复检哪些状态。

一个新的受控工具通常涉及：

```text
hermes/tools/<tool_name>.py
    业务 handler、工具 schema、ToolRegistry 注册

hermes/tools/<tool_name>_approval.py
    参数规范化、风险判断、Binding、审批决策、Grant 复检和 Handler 注册

hermes/tools/__init__.py
    在 register_all() 中调用工具 register()
```

工具准备执行时，先由自己的 approval 模块生成 `ApprovalAssessment`。其中的 `details` 使用统一信封：

```python
{
    "binding_version": 1,
    "binding": {
        # 只放该工具执行前必须重新确认的状态
    },
    "fingerprint": "sha256:...",
    "operation_type": "example.write",
    "risk_level": "high",
    "allowed_grant_scopes": ["once"],
}
```

Binding 必须是可 JSON 序列化的字典。它应覆盖参数本身无法表达、但状态变化后必须让批准失效的信息。例如文件工具保存规范化路径和文件快照，外部模型调用保存 provider、model 和输入文件状态。工具参数、会话或 Binding 中任意内容改变后，稳定指纹都会改变。

每个受控工具实现一个 `ApprovalHandler`：

```python
class ExampleApprovalHandler:
    def validate_request_binding(
        self, *, arguments: dict, binding: dict, session_key: str
    ) -> bool:
        """从公开参数和会话重建 Binding 语义，拒绝缺字段或不一致状态。"""
        ...

    def validate_grant_binding(
        self, *, arguments: dict, binding: dict, session_key: str
    ) -> bool:
        """签发可信 Grant 前再次执行同样严格的校验。"""
        ...

    def build_session_rule(self, grant):
        """不支持 session grant 的工具直接返回 None。"""
        return None

    def session_rule_matches(self, rule, runtime_context: dict) -> bool:
        """不支持 session grant 的工具直接返回 False。"""
        return False
```

Handler 只解释本工具的 Binding。它不写数据库，不操作 Gateway 队列，也不执行工具。文件、页面或外部目标的当前状态复检仍由 approval 模块提供 helper，业务 handler 在真正产生副作用前调用；不一致时统一返回 `approval_stale`。

approval 模块应提供自己的注册函数，并保护同名 Handler 不被替换：

```python
_HANDLER = ExampleApprovalHandler()


def register_example_approval_handler() -> None:
    registered = get_approval_handler("example_action")
    if registered is None:
        register_approval_handler("example_action", _HANDLER)
    elif registered is not _HANDLER:
        raise ValueError(
            "approval handler already registered: example_action"
        )
```

工具的 `register()` 先调用这个审批注册函数，再向 `ToolRegistry` 注册同名工具：

```python
def register(registry) -> None:
    register_example_approval_handler()
    registry.register(
        name="example_action",
        toolset="example",
        schema=EXAMPLE_SCHEMA,
        handler=handle_example_action,
        execution_environments=("cli", "gateway"),
        unattended_allowed=False,
        approval_mode="interactive_or_remote",
        risk_level="high",
        default_enabled_environments=(),
        retry_safe=False,
        unknown_on_crash=True,
    )
```

创建或恢复审批时，系统会依次确认：工具当前已注册、当前入口策略允许该工具、工具声明需要审批、同名 Approval Handler 已注册、Binding 能被 Handler 重建、完整参数和会话对应的指纹一致。任一步失败都不能创建或恢复审批。

只有低风险或中风险工具确实需要会话级授权时，才实现 session rule。规则对象由工具自己的 Handler 构造和解释；公共审批层只按会话和工具名保存不透明规则。一次性工具必须返回 `None` 和 `False`，不要为 Browser、Media 或外部发送类工具增加长期授权。

新增受控工具不应修改：

- `hermes/approval_policy.py`
- `hermes/approval_handlers.py`
- `hermes/persistence/`
- `hermes/gateway/runner.py`
- `TrustedApprovalGrant`

如果发现必须在这些公共模块中增加工具名分支，说明工具专用的 Binding 构造或校验仍放错了位置。

## 接入到不同运行环境

### CLI

普通 CLI 工具通常只需要在注册元数据中声明 `cli`。高风险操作可以使用现有交互审批机制。

主要相关模块：

- `hermes/conversation.py`
- `hermes/tools/__init__.py`
- 对应工具自己的 `<tool_name>_approval.py`

### Gateway

如果工具只是在飞书或微信会话中被模型调用，通常不需要修改 `GatewayRunner`。声明支持 `gateway`，并在对应平台配置的 toolsets 中启用即可。

只有以下情况才修改 Gateway：

- 接入新的消息平台；
- 需要平台特有的上传或发送协议；
- 需要 Outbox、runtime lease 或进程重启恢复；
- 需要远程审批界面或平台身份。

主要相关模块：

- `hermes/gateway/adapters/`
- `hermes/gateway/runner.py`
- `hermes/gateway/outbound_delivery.py`
- `hermes/gateway/persistence.py`

新增平台时应实现 `BasePlatformAdapter`，不要把平台 HTTP 协议直接写进 Runner。

### Cron

工具要进入 Cron，必须同时满足：

- 注册元数据明确包含 `cron`；
- `unattended_allowed=True`；
- CronJob 显式申请对应 toolset；
- 当前 `CronCapabilityGrant` 包含该工具和能力范围；
- 运行时 `CronCapabilityGuard` 校验通过。

新增工具不会自动扩大已有 CronJob 的权限。Cron 内仍禁止 Cron 管理工具和默认后台 Delegate。

主要相关模块：

- `hermes/cron/capability.py`
- `hermes/cron/executor.py`
- `hermes/cron/tool.py`
- `hermes/persistence/cron.py`

如果新能力会扩大文件、Terminal、网络或投递范围，需要把相关约束加入规范化 capability scope，使审批展示、fingerprint、持久 grant 和运行时校验使用同一份数据。

### Delegate

声明支持 `delegate` 后，工具仍会经过子 Agent 的限制策略。不要让 Delegate 自动继承主会话全部权限，也不要开放递归创建子 Agent 的能力。

主要相关模块：

- `hermes/tools/delegate.py`
- `hermes/delegate_jobs.py`
- `hermes/tools/__init__.py`

## 什么时候需要数据库

以下情况通常需要持久化：

- 进程重启后必须继续处理；
- 用户需要查询历史或审计记录；
- 操作包含 claim、重试、状态机或并发竞争；
- 数据是长期业务事实，而不只是当前模型调用结果。

接入顺序：

1. 在 `hermes/persistence/schemas/` 增加最新版 DDL；
2. 在 `hermes/persistence/migrations/` 增加版本迁移；
3. 在 `hermes/persistence/schema.py` 提升 schema version 并接入迁移；
4. 在对应领域文件中提供事务化数据访问接口；
5. 上层工具和服务只调用持久化接口，不直接散写 SQL。

简单查询、即时计算和普通网页搜索结果通常不需要新增数据库表。

## 联网搜索接入示例

建议新增 `hermes/tools/web_search.py`，包含搜索服务接口、参数校验、结果截断、稳定错误分类和工具注册。

至少需要处理：

- 查询长度和结果数量限制；
- 请求超时与临时错误；
- 允许访问的搜索服务；
- 不把凭据、环境变量、完整文件内容或本地隐私路径自动放入查询；
- 将网页内容视为外部不可信数据；
- 返回来源地址，便于模型生成可核验答案。

按请求创建并关闭 HTTP 客户端时，不需要修改 Gateway。如果要供 Cron 使用，还需要为外部通信能力增加 capability 约束。

## MCP 接入示例

MCP 工具是连接后动态发现的，建议增加一个小型独立目录：

```text
hermes/mcp/
├─ __init__.py          MCP 对外接口
├─ client.py            连接、调用和关闭
├─ catalog.py           远程 schema 规范化与名称映射
└─ policy.py            本地 allowlist、风险和运行环境策略
```

推荐流程：

```text
读取 MCP Server 配置
→ 建立连接并获取远程工具目录
→ 使用本地 allowlist 和策略过滤
→ 给工具名增加 server 前缀
→ 注册到 ToolRegistry
→ 当前会话再按 ToolPolicy 解析
→ 调用时由 MCP client 转发
```

远程 Server 返回的工具声明不能直接当成本地授权。新出现的远程工具必须先匹配本地策略，否则不能进入任何会话。只有 MCP 连接需要随 Gateway 启停时，才把 manager 的启动和关闭挂到 Gateway 生命周期；MCP 调用逻辑本身不要写入 Runner。

## 自进化功能接入建议

自进化不应直接实现成一个拥有无限权限的工具。建议拆成独立领域流程：

```text
收集运行反馈
→ 生成候选改进
→ 静态检查和风险评估
→ 用户审批
→ 在受限工作区应用
→ 验证结果
→ 成功提交或失败回滚
```

可能涉及：

- 独立的 `hermes/evolution/` 领域模块；
- ToolRegistry 中的候选生成、查看和应用工具；
- approval policy；
- 候选、审批和应用结果的持久化；
- 文件快照或版本控制回滚。

生成建议和实际修改必须分开授权。Cron 无人值守任务不应默认获得应用代码变更的权限。

## 接入前检查清单

- 功能是否已有清晰的程序级接口？
- 模型 handler 是否只是参数转换和结果序列化？
- 是否只注册了一次？
- toolset 和支持环境是否为最小集合？
- 是否正确声明审批、风险、无人值守和重试语义？
- 需要审批时，是否注册了同名 Approval Handler？
- Handler 能否从 arguments、session 和 Binding 重建完整操作身份？
- 工具是否在产生副作用前复检当前状态并返回 `approval_stale`？
- 不支持 session grant 的 Handler 是否明确返回 `None` 和 `False`？
- 是否避免模型参数覆盖可信身份、授权或路由信息？
- 是否真的需要修改 Gateway？
- 是否真的需要新增数据库状态？
- Cron 使用时是否进入 capability scope 和运行时 Guard？
- 外部内容、日志和错误提示是否做了截断与脱敏？
